# FAST-LIVO2 一键回归测试脚本 设计

日期：2026-07-26
状态：已确认，待实施

## 1. 背景

改动 FAST-LIVO2 源码或配置后，需要快速回答一个问题：**算法效果变了没有？**

难点在于 FAST-LIVO2 的输出**不可复现**。[vio.cpp:1631](../../../src/FAST-LIVO2/src/vio.cpp#L1631) 有
`#pragma omp parallel for reduction(+ : error, n_meas)`（4 线程，线程数由
[CMakeLists.txt:63](../../../src/FAST-LIVO2/CMakeLists.txt#L63) 写死为 `MP_PROC_NUM=4`），
浮点归约的合并顺序 run-to-run 不固定；`error` 参与迭代收敛判断，某一帧跨过阈值即翻转，
之后轨迹一路发散。

2026-07-26 在 `dataset/livo_2026-07-25-22-50-36.bag`（52s，508 帧 LiDAR / 511 帧有效图像，
18.3m 闭合行走）上实测 4 轮（2×1x + 2×5x），32 核 WSL2：

| 类型 | 对比 | 最大偏差 | 末帧偏差 |
| --- | --- | --- | --- |
| 同倍速 | 1x vs 1x_b | 0.1828 m | 0.0535 m |
| 同倍速 | 5x vs 5x_b | 0.1121 m | 0.0349 m |
| 跨倍速 | 1x vs 5x | 0.1990 m | 0.0282 m |
| 跨倍速 | 1x vs 5x_b | 0.2019 m | 0.0376 m |
| 跨倍速 | 1x_b vs 5x | 0.1222 m | 0.0610 m |
| 跨倍速 | 1x_b vs 5x_b | 0.1843 m | 0.0279 m |

两个结论直接决定本设计：

1. **同倍速重跑两次也会差 ~5cm / ~18cm**，所以"位姿完全不变"不是可达的验收标准，
   判据必须是"偏差落在噪声基线内"。
2. **跨倍速差异与同倍速噪声完全重叠**，5x 回放不引入可检测的误差，
   因此对比运行默认可以用加速回放来省时间。

## 2. 目标与非目标

**目标**：改代码前用指定数据源生成基线（轨迹 + 噪声阈值），改完之后一条命令跑出
PASS / FAIL，判据可解释、可复现。

**非目标**：

- **不比对点云地图**。测试运行关闭 `pcd_save`（配置里 `interval: -1` 会把整张图堆在内存里）。
  轨迹作为效果代理能覆盖绝大多数回归，但**纯建图侧、不影响位姿的改动测不出来**。
- **不做精度评测**。没有真值轨迹，本工具只回答"相对基线变没变"，不回答"准不准"。
- **不测实时性回归**。耗时会打印出来供人看，但不作为 PASS/FAIL 判据。

## 3. 目录结构

沿用 `collect/collect.sh` 的范式（bash 入口 + 独立 launch + readme 文档）：

```text
test/
  regress.sh        # 一键入口
  regress.launch    # 建图节点 + republish
  compare_traj.py   # 轨迹对比与阈值计算
  baseline/<名字>/
    traj.txt        # 基线轨迹（TUM 格式）
    meta.json       # 元信息与阈值
  .work/            # 运行产物（节点日志 / RSS 采样 / 临时轨迹），gitignore
```

`regress.sh` 用 `readlink -f "${BASH_SOURCE[0]}"` 解析自身路径推导工作区根目录，
任意目录可调用，可软链到 `~/.local/bin/`。

`test/.work/` 加入根 `.gitignore`。`test/baseline/` 入库（每套约 40KB）。

### 为什么需要独立的 regress.launch

`mapping_mid360.launch` 不能直接复用：

- `evo/pose_output_en` 默认 false，不写轨迹
- `evo/seq_name` 固定，并发/多轮会互相覆盖
- `pcd_save/pcd_save_en` 为 true 且 `interval: -1`，会把整张图堆内存

`regress.launch` 先 `rosparam load` 同一份 yaml，再用 `<param>` 覆盖这三项，
并保留 `image_transport republish` 节点（bag 里存的是 `/left_camera/image/compressed`）。
`cfg` / `cam_cfg` 作为 launch arg，默认 `mid360.yaml` / `camera_pinhole_mid360.yaml`，
以便支持公开数据集。

节点把轨迹硬编码写到 `ROOT_DIR/Log/result/<seq_name>.txt`（submodule 内，已被其
`.gitignore` 的 `Log/*` 覆盖，不会弄脏 submodule）。脚本用唯一 `seq_name` 运行，
结束后把结果移到 `test/.work/`。

## 4. 命令行

```bash
./test/regress.sh baseline <bag> [-n 名字] [-r 轮数] [--cfg <yaml>] [--cam-cfg <yaml>]
./test/regress.sh check [-n 名字] [--rate <倍速>]
./test/regress.sh list
```

默认值：

| 参数 | 默认 | 说明 |
| --- | --- | --- |
| `-n 名字` | bag 文件名去掉扩展名 | 基线目录名 |
| `-r 轮数` | 3 | 基线轮数，固定 1x |
| `--rate` | 5 | check 的回放倍速 |
| `--cfg` | `mid360.yaml` | 主配置 |
| `--cam-cfg` | `camera_pinhole_mid360.yaml` | 相机配置 |

`check` 不指定 `-n` 时，若 `test/baseline/` 下只有一套基线就用它，
多于一套则报错并列出可选值（退出码 2）。

`list` 列出 `test/baseline/` 下每套基线的名字、生成日期、bag 名、轮数与四项阈值，
用于确认手头有哪些基线可用。

## 5. baseline 流程

1. 校验 bag 存在；用 `rosbag info` 取文件大小与各话题消息数作为身份指纹
   （不用 md5：数据集里有 21GB 的包，全文件哈希太慢）。
2. 以 1x 跑 N 轮，每轮唯一 `seq_name`，收集轨迹与运行日志。
3. 每轮提取硬指标：LiDAR 帧数、有效图像帧数、轨迹点数。
   N 轮硬指标必须全部一致，否则报错退出（码 2）—— 说明环境本身不稳定，基线不可信。
4. N 条轨迹两两对比（N(N-1)/2 组），对每个轨迹指标取全组最大值。
5. 阈值 = 该最大值 × 安全系数（默认 2.0）。
6. 选**中位轨迹**存为 `traj.txt`：到其余 N-1 条轨迹的位置 RMSE 之和最小的那条，
   比"取第一条"更有代表性。
7. 写 `meta.json`。

### 有效图像帧数的定义

统计节点日志里 `Get image, its header time: <t>` 且 `<t>` 大于首帧 LiDAR 时间的条数。

原因：实测发现 `livo_2026-07-25-22-50-36.bag` 开头 8 帧图像的 header 全部卡在同一个
陈旧值（`1590192351.9004`，相机驱动首次触发同步前发出），之后跳 452.3s 才接上真实时间。
这些帧在第一帧 LiDAR 到达前就被 `img_cbk` 丢弃，从不进入解算；而 `image_transport
republish` 队列深度为 1（上游 `image_common` noetic-devel 的 `republish.cpp` 中
subscribe 与 advertise 均为 1），加速回放时丢的正是这批帧——实测 1x 收到 6 帧垃圾帧、
5x 只收到 2~4 帧，但四轮的**有效帧数都是 511**。

若把垃圾帧计入硬指标，会因为与解算无关的抖动产生假失败。

## 6. check 流程

1. 加载 `meta.json`；比对 bag 指纹，不一致则报错退出（码 2）。
   比对机器名，不一致则打印提示（不影响判定）。
2. 以 `--rate` 跑 1 轮，同时按 0.5s 间隔采样 `fastlivo_mapping` 进程的 `VmRSS`。
3. **积压检测**（见 §7）。命中则退出码 3。
4. **硬指标核对**：LiDAR 帧数、有效图像帧数、轨迹点数与基线不等即 FAIL。
5. **轨迹指标核对**：超阈值即 FAIL。
6. 打印结果表，按 §8 返回退出码。

## 7. 积压检测

5x 结果可信的前提是算法跟得上。`rosbag play` 退出后，脚本以 **0.2s 间隔**轮询轨迹文件
行数直到稳定，这段时间即排空耗时。两个信号，任一命中即判定结果不可信：

- **排空耗时 > 3.0s（绝对值）**。跟得上时排空基本是瞬时的，落后时会随积压量线性增长。
- **RSS 单调增长**。取采样序列后半段做线性拟合，斜率 > 10 MB/s 判定为积压。
  实测四轮峰值 955 / 966 / 975 / 984 MB，跟得上时基本持平。

命中时打印实测数值并提示 `--rate 1` 重跑。

**为什么用绝对值而不是"排空/回放"比值**：2026-07-26 的实验脚本用 2s 轮询，四轮测得的
排空耗时都恰好是 2.0s —— 那是**轮询间隔的测量下限，不是真实排空耗时**。按该数据推出的
比值（1x 为 3.8%、5x 为 18%）会让任何 25% 量级的比值阈值贴着 5x 的正常值，
换台稍慢的机器就误报。改用 0.2s 轮询 + 绝对阈值可避开这个陷阱。
实施时需重新实测正常情况下的排空耗时，若普遍超过 1s 则上调该阈值。

## 8. 判据与退出码

**硬指标**（与基线不等即 FAIL）：LiDAR 帧数、有效图像帧数、轨迹点数。

**轨迹指标**（超阈值即 FAIL），在两条轨迹的共同时间戳上计算：

| 指标 | 说明 |
| --- | --- |
| 位置 RMSE | 逐帧位置欧氏距离的均方根 |
| 末帧偏差 | 最后一个共同时间戳上的位置距离 |
| 最大偏差 | 逐帧位置距离的最大值 |
| 最大姿态偏差 | 逐帧四元数相对旋转角的最大值（度） |

共同时间戳数量少于基线轨迹点数的 95% 即 FAIL。这条与硬指标里的"轨迹点数相等"不重复：
硬指标只看条数，两条轨迹可以点数相同但时间戳错开——那说明更新调度变了，同样是回归。

**不做 Umeyama 对齐**：两轮从同一原点、同样初始化开始，不对齐更敏感，正是回归检测
想要的。因此该指标**不叫 ATE**，就叫位置 RMSE，避免名实不符。

退出码：

| 码 | 含义 |
| --- | --- |
| 0 | PASS |
| 1 | FAIL（硬指标或轨迹指标越界） |
| 2 | 环境/运行错误（bag 缺失、基线不存在或不唯一、节点崩溃、基线内部不一致） |
| 3 | 结果不可信（检测到积压） |

积压单独用码 3 而不是并入 FAIL：跟不上倍速时的输出既不能证明变了、也不能证明没变，
不该伪装成任一结论。

## 9. meta.json

```json
{
  "name": "livo_2026-07-25-22-50-36",
  "created": "2026-07-26T12:00:00+08:00",
  "bag": {
    "path": "dataset/livo_2026-07-25-22-50-36.bag",
    "size_bytes": 257450182,
    "topics": {"/livox/lidar": 508, "/livox/imu": 10163, "/left_camera/image/compressed": 519}
  },
  "cfg": "mid360.yaml",
  "cam_cfg": "camera_pinhole_mid360.yaml",
  "commit": "c97b73e",
  "submodule_commit": "d1c113b",
  "host": "uplume",
  "runs": 3,
  "rate": 1,
  "hard": {"lidar_frames": 508, "valid_images": 511, "traj_points": 504},
  "safety_factor": 2.0,
  "observed": {"pos_rmse": 0.0344, "final": 0.0535, "max": 0.1828, "max_rot_deg": 3.1837},
  "threshold": {"pos_rmse": 0.0688, "final": 0.1070, "max": 0.3656, "max_rot_deg": 6.3674}
}
```

`observed` 保留实测噪声原值，便于判断某次 FAIL 是"刚好越界"还是"差一个量级"。

上例中的 `observed` 是 2026-07-26 两轮 1x 实测值（`run_1x` vs `run_1x_b`，504 个共同时间戳），
不是构造数据。注意**最大姿态偏差达 3.18°** —— 姿态噪声远比位置噪声显眼，
定阈值时不要凭直觉猜这个量级。

## 10. 已知限制

- 阈值由本机噪声推导。换机器（尤其 CPU 核数不同，影响 OpenMP 线程划分）建议重建基线；
  `host` 不匹配时脚本会提示。
- N=3 只有 3 组两两对比，噪声估计偏乐观。`-r 5` 可得 10 组，代价是基线生成耗时约 5 分钟
  （以本包 54s/轮计）。
- 安全系数 2.0 是经验值，不是统计置信区间。真实回归若小于噪声的 2 倍将检测不到。
- 不覆盖点云地图质量（见 §2 非目标）。
